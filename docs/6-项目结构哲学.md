# agent-stack v2 项目结构哲学

这份文档不是装饰性说明，而是后续修改本项目时的边界检查表。目标是让任何新功能都能回答三个问题：它属于哪一层、由谁决定是否启用、失败后从哪里恢复。

## 一、总原则

### 1. 先分层，再写功能

项目按以下责任链组织：

```text
HTTP / 浏览器
    -> router.py / models.py
    -> agent.py
    -> runtime/assist.py
    -> runtime/registry.py
    -> runtime/* capability modules
    -> memory.py / rag_store.py / observability/
```

- `router.py` 只负责 HTTP、鉴权入口、请求参数、SSE 封装和根 trace。
- `models.py` 只负责接口数据结构，不放业务判断。
- `agent.py` 只负责 Agent 状态机、模型循环、工具调用顺序和 SSE 事件。
- `runtime/assist.py` 只负责输入整理和本轮能力选择，不执行网络、文件或浏览器工作。
- `runtime/registry.py` 只负责统一分发，不决定用户意图。
- `runtime/` 下每个文件代表一类完整能力，能力内部的 schema、执行和错误边界放在一起。
- `memory.py` 只负责上下文与会话记忆，不负责选择工具。
- `observability/` 只旁路记录，不改变业务结果。

### 2. 用户意图决定加载，不是用户决定工具

用户不应该看到“请选择工具”。程序根据模式和输入决定本轮暴露什么：

- 聊天模式：正常讨论；需要外部事实时自动给网页检索和页面读取。
- 计划模式：网页检索、页面读取、结构化拆题按阶段启用。
- 文件、图片、项目源码、终端和浏览器能力只在命中对应意图时加入本轮。
- 普通对话不应因为某个大依赖存在，就把它加载或把它的 schema 塞进上下文。

### 3. 可观察优先于“看起来能跑”

每一层失败都必须留下可定位信息：

- 请求：`session_id`、模式、模型、附件数量。
- 阶段：receive、tool、answer、done。
- 工具：名称、来源、参数长度、成功/失败、错误类型、耗时。
- 模型：输入输出 token、缓存 token、是否有工具调用、异常类型。
- 恢复：原始错误、是否进入恢复、恢复是否成功、复核分数。

日志不记录模型密钥、完整附件、完整用户隐私内容和工具参数正文。

## 二、核心状态

### 1. 会话状态

服务端 `router.sessions` 是运行时会话事实源；`HybridMemory` 保存该会话的短期消息、摘要、RAG 隔离信息和工具失败反思。

浏览器 `localStorage.transcripts` 只是界面快照，用来刷新后恢复画面，不能替代服务端记忆，也不能反向覆盖服务端会话。

如果将来需要重启保留会话，应新增持久化 SessionStore，不要把 SQLite 读写混进 `agent.py` 或前端。

### 2. Agent 阶段

`runtime/phase.py` 是阶段的唯一来源：

```text
RECEIVE -> TOOL -> ANSWER -> DONE
```

计划模式的“拆题、查资料、复核”是工具阶段内部的子流程，不另造一套与 `Phase` 平行的状态枚举。阶段提示通过 `memory.phase_hint` 注入上下文；日志和前端状态都使用同一个阶段值。

网页类计划不能只输出功能清单：

- `web_game` 必须写坐标系、数组映射、可见/隐藏区、状态机、不变量、规则数据、循环终止条件。
- 浏览器功能必须区分静态检查和真实浏览器人工验收。
- “按标准实现”必须落成具体数据、常量、测试操作和预期结果，或标记待查询来源。
- 高风险交互（失焦、后台、触摸、动画、计时器）必须有失败路径。

### 3. 工具调用消息完整性

任何模型返回的 `tool_calls` 都必须逐个生成对应的 `tool` 消息，且 `tool_call_id` 一一匹配。不能为了去重而跳过一个 tool call，否则上游会返回：

```text
assistant message with tool_calls must be followed by tool messages
```

去重只允许发生在 schema 暴露或执行缓存层，不能发生在消息配对层。

## 三、能力模块

### 1. 对话辅助

| 能力 | 文件 | 启用条件 |
|---|---|---|
| 本轮能力选择 | `runtime/assist.py` | 每轮轻量执行 |
| 公开检索 | `runtime/web_lookup.py` | 聊天/计划需要外部事实 |
| 页面浏览 | `runtime/browser_tool.py` | 需要执行页面脚本或查看页面 |
| 项目查找 | `runtime/project_lookup.py` | 用户问源码、文件和行号 |
| 会话查找 | `runtime/session_lookup.py` | 用户提到刚才、之前、上文 |
| 英文释义 | `runtime/word_lookup.py` | 英文单词释义意图 |
| 计划结构 | `runtime/brief.py` | `mode=plan` |
| 终端 | `runtime/shell_tool.py` | 用户明确要求命令结果 |

每个能力模块都应保持：schema、输入校验、执行、超时、错误返回在同一文件。跨能力共用的循环才进入 `registry.py`。

### 2. 附件能力

`runtime/ingest.py` 是兼容层，不实现 PDF、OCR、表格解析算法：

- 文档交给 MarkItDown。
- PDF/扫描类能力交给 Docling。
- 图片是否发送由模型视觉能力门禁决定。
- 不支持视觉的模型在模型请求前直接返回，不上传图片、不浪费模型调用。

## 四、计划模式

计划不是普通回答的长版本，而是可交给其他项目继续使用的结构化产物：

1. 读取本会话中已有需求和偏好。
2. 查找已有流程和参考资料。
3. 生成至少 12 个可执行细项，每条第一选项是默认方案。
4. 对草稿独立复核并最多重写一次。
5. 独立质量评分，评分和缺口进入结构。
6. 只在用户需要许可证、付费资格或确实无法推进时留下附加信息。

计划失败时的恢复顺序：

```text
工具参数错误 -> 读取当前会话 -> 一次结构恢复 -> 一次复核 -> 明确错误
```

禁止：无限重试、把不完整结构伪装成完成、把复核失败伪装成高分。

## 五、修改规则

新增功能前先回答：

1. 这是 HTTP、编排、能力、记忆还是观测问题？
2. 是否应该按需加载？
3. 是否改变了冻结接口？
4. 失败时用户看到什么，日志记录什么，是否能重试？
5. 是否需要独立 `verify/` 脚本？

禁止的改法：

- 把所有新工具继续堆进 `tools_local.py`。
- 在前端偷偷改变后端事实。
- 在 Agent 循环里直接写供应商、文件格式或浏览器细节。
- 用一个宽泛 `except Exception` 把错误变成“空回复”。
- 为了去重跳过 tool call 对应消息。
- 没有验证输出就声称功能完成。

## 六、验收方式

每次结构性修改至少执行：

```powershell
cd agent-lite
& "D:\Miniconda3\envs\my-agent-env\python.exe" -m compileall -q .
& "D:\Miniconda3\envs\my-agent-env\python.exe" verify\verify_runtime.py
& "D:\Miniconda3\envs\my-agent-env\python.exe" -m pytest tests/ --ignore=tests/test_eval.py -q
```

真实输出必须保留。专项验证失败时先修实现，不修改 `agent-lite/tests/` 凑绿。

## 七、模板演进

模板更新不能只增加几句提示词。每次新增或修改类型模板必须同时检查：

1. 通用基座规则是否仍然存在。
2. 用户事实是否优先于模板默认。
3. 可见决策是否仍限制为 2 到 3 个选项。
4. 隐藏细节、验收和资源申请是否仍保留。
5. 新增特化检查是否有 `verify/` 专项断言。

模板是增量合并，不是互相覆盖。新增网页游戏规则不能让网页通用规则、资源申请或失败恢复消失。
