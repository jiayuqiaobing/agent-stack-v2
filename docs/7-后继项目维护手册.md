# 后继项目维护手册

这份文件给之后接手本项目的模型、开发者和自动编程代理使用。它不是“建议”，而是修改基座时必须遵守的操作顺序。

## 1. 先理解项目是什么

这是一个可扩展的 Agent 基座，不是某一个具体业务的脚本集合。它提供：

- 多会话聊天。
- 聊天/计划两种模式。
- 按需启用网页、浏览器、项目查找、文件、终端、附件和 MCP 能力。
- 短期上下文、摘要、RAG 隔离。
- 真流式 SSE、工具调用事件、阶段事件。
- trace/span JSONL、文本日志和 `/metrics`。
- 独立验证脚本和不可修改的回归测试。

前端还必须遵守视觉基线：历史会话在聊天区顶部标签栏；侧栏收起后保留窄轨和顶部折叠按钮；操作图标使用页面内自制静态 SVG 线稿；悬停、焦点、窄屏和减少动态效果保持统一。前端改动必须用 Playwright 做真实浏览器验收。

业务项目应该通过新增能力模块、技能文件或路由适配接入，而不是复制一份 Agent 主循环。

## 3. 如何新增一个方向

“方向”指一个可以独立启用的能力，例如数据库查询、图像检索、代码仓库分析或第三方 API。

### 必须建立的边界

1. 在 `runtime/<capability>.py` 放 schema、输入校验、执行函数、超时和错误返回。
2. 在 `runtime/assist.py` 增加一个清晰的意图判断，或从显式模式启用。
3. 在 `runtime/assist.py:run_assist()` 加懒加载入口。
4. 不在 `agent.py` 里写具体网络协议、文件格式和供应商逻辑。
5. 需要外部连接时，默认按需创建，不能在服务启动时无条件连接。
6. 给 `verify/verify_runtime.py` 或新的 `verify/verify_<capability>.py` 加不依赖真实模型的检查。
7. 说明能力的来源、依赖、权限边界、超时和失败行为。

### 能力模块模板

```python
CAPABILITY_TOOL = {
    "type": "function",
    "function": {
        "name": "capability_name",
        "description": "模型什么时候用它，以及不会做什么",
        "parameters": {"type": "object", "properties": {}, "required": []},
    },
}


async def capability_name(**args) -> str:
    try:
        # 只放该能力的实现；外部依赖在这里或函数内部懒加载。
        return "结果"
    except TimeoutError:
        return "错误: 能力超时"
    except Exception as exc:
        logger.warning("能力失败 name=%s error=%s", "capability_name", type(exc).__name__, exc_info=True)
        return f"错误: 能力失败: {type(exc).__name__}"
```

## 4. 如何修改 Agent 循环

尽量不要修改 `agent.py`。必须修改时遵守：

- 所有模型响应都先检查 `choices`、`message`、`tool_calls` 是否存在。
- 每个 assistant `tool_call` 必须对应一个 `tool` 消息。
- 不能为了去重而跳过 tool message；去重只能在 schema 或执行缓存层。
- 流式和非流式逻辑必须保持同一套工具协议。
- 计划错误必须走“恢复一次 -> 复核一次 -> 明确失败”，不能无限重试。
- 新阶段提示放进 `runtime/phase.py`，通过 `memory.phase_hint` 进入上下文。
- 所有失败都要保留错误类型、session、阶段和工具名。

## 5. 如何修改上下文

`HybridMemory.build_context()` 是上下文唯一组装点。不要在 `router.py`、工具文件或前端各自拼一份历史。

上下文顺序：

1. 稳定 system prompt。
2. 净化后的会话消息。
3. RAG 相关记忆。
4. 阶段提示和工具失败反思。

供应商扩展字段不能无条件回传。任何新的模型私有字段都要先确认目标供应商是否接受，否则只保存在内部日志或内部状态。

## 6. 日志和定位方法

### 文本日志

位置：`agent-lite/logs/agent-lite.log`，每天轮换，保留 14 天。每行包含：

- 时间和级别。
- logger 名称。
- `trace`、`span`、`session`。
- 事件描述。

### 结构化 span

位置：`agent-lite/logs/spans-YYYY-MM-DD.jsonl`。

- `agent.turn`：请求边界。
- `llm.chat`：模型调用、token、缓存、工具调用标记。
- `tool.<name>`：工具来源、参数长度、成功、错误类型、耗时。
- `rag.search`：检索命中和降级。
- `memory.summarize`：摘要压缩。

### 排查顺序

1. 先取用户看到的错误时间和 session。
2. 在文本日志里按 session 找阶段转换。
3. 用 trace_id 找同一请求的所有 span。
4. 看最后一个成功阶段和第一个失败 span。
5. 检查上下文中是否存在残缺 tool-call 链。
6. 再决定改能力、编排、供应商适配还是前端。

禁止只看最终回复猜原因；也禁止把异常改成“空回复”。

## 7. 前端与后端契约

SSE 事件保持兼容：

- `session`：返回 session id。
- `status`：阶段文字。
- `delta`：文本片段或结构化计划文本。
- `tool_call`：工具过程展示。
- `usage`：token 统计。
- `done`：本轮完成。
- `error`：可展示错误。

前端 `localStorage` 只保存渠道、模式和 transcript 快照。删除会话时必须先删除本地快照，再删除服务端 session，不能通过“打开空会话”触发旧会话快照覆盖。

## 8. 每次改动的固定流程

1. 先读 `AGENTS.md`、`LESSONS.md` 和本文件。
2. 明确改动属于哪一层。
3. 先写 `verify/` 独立验证。
4. 实现最小修改。
5. 对每个新文件运行 AST/compile 检查。
6. 跑专项验证。
7. 跑回归：`pytest tests/ --ignore=tests/test_eval.py -q`。
8. 检查 `git diff --check`、`git status`，确认没有碰 `.env`。测试失败不得改松断言。
9. 汇报真实输出、改动文件和遗留问题。

## 9. 后继项目接入方式

后继项目不要复制 `agent.py`。推荐做法：

- 复用 `runtime/` 能力模块。
- 用新的 `SYSTEM_PROMPT_BASE` 或技能目录替换业务身份。
- 用新的 `ChatRequest` 扩展业务字段，但保留 `session_id`、SSE 和工具协议。
- 业务专属状态放在独立的 `runtime/<business_state>.py`，不要塞进 `memory.py`。
- 业务资源库通过独立适配器接入 `rag_store.py` 的接口边界。
- 新的前端只消费稳定 SSE 事件，不读取 Python 内部对象。

## 10. 网页和游戏项目不可省略的工程约束

不要只把“按钮、页面、功能”列成清单。网页游戏模板必须要求：

- 坐标原点、数组下标、屏幕映射、可见区和隐藏区。
- 状态机、数据不变量和所有循环终止条件。
- 标准规则的具体数据表、常量或待查询来源。
- 每条验收包含操作步骤和预期结果。
- 静态检查与真实浏览器验收分开记录。
- 失焦、切后台、触摸、动画、计时器和十分钟压力测试。

页面能通过 AST 或静态检查，不等于网页完成。必须真实打开并操作浏览器。

这样新增网页项目、资料筛选项目、代码审查项目时，改变的是能力和策略，不是重新发明整个 Agent 基座。

## 10. 规划模板扩展

新增项目方向时，优先新增 `runtime/planner/templates.py` 的模板和对应验证，不要把方向判断写进 `agent.py`。

模板必须提供：

- 触发词和类型名称。
- 必须覆盖的章节。
- 类型专属检查项。
- 需要查询端研究的资源类型。
- 静态验收和真实运行验收的区别。

没有通用模板。未命中已知类型时，不得套用网页、软件或游戏章节。已命中的类型只提供隐藏检查，可见正文必须来自用户原话和检索结果。模板不得重新询问用户已经确认的事实，也不得把所有实现细节变成可见问题。不同问题的可见标题和默认句不得相同。

### 10.1 能力覆盖矩阵

通用能力和特化能力维护在 `runtime/planner/coverage.py`。新增或修改类型时必须同步更新：

1. `runtime/planner/templates.py` 的触发词、章节和检查项。
2. `runtime/planner/coverage.py` 的特化能力集合。
3. `verify/verify_runtime.py` 的类型识别与覆盖断言。
4. 本手册中的矩阵和真实验收说明。

模板是增量合并，不是互相覆盖。更新网页游戏不能丢掉通用验收、资源申请或风险；新增跨类型能力应进入能力模块或覆盖矩阵，而不是复制多份提示词。
