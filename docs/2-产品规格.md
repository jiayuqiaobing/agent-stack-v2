# 2 · 产品规格

> **这份文档回答「v2 要做什么、做到什么程度算完成」。**
> 它给**人**看（你 + 面试官），不下发执行细节 —— 下发用 `4-执行规格.md`。
>
> 配套文档：`1-接口冻结.md`（不许变的东西）、`3-可观测数据模型.md`（新增契约）

## 1. 目标

### 1.1 定位（2026-09-23 确认）

**这是一个「能力证明」项目** —— 目的是证明作者**能独立写出这样一个东西**。

它**不是**：
- ❌ 不是为了日活/用户量（没有用户）
- ❌ 不是为了技术炫技（不堆没必要的复杂度）

**它是要在下面三个问题上，各交付一份"可演示、可复现、经得起追问"的证据**：

| # | 要证明的能力 | 交付的证据 |
|---|-------------|-----------|
| 1 | 我知道一个 AI 系统**上线后该怎么度量** | 端到端 trace/span + 评估集能跑出分数 |
| 2 | 我知道**它坏了怎么办** | 拔掉主上游，服务仍可用 |
| 3 | 我知道**多 Agent 该怎么受控地编排** | 两级子代理，有并发上限 |

### 1.2 一句话

> **v1 证明了"能跑通"，v2 证明"能运营"：**
> **一个 AI 系统上线后，你怎么知道它好不好、贵不贵、坏了怎么办。**

三个能力各有归属，不是并列的功能清单：
- **可观测** 回答「好不好、贵不贵」
- **评估** 回答「改动之后是变好还是变坏」
- **网关容错** 回答「坏了怎么办」

### 1.3 判据

**"做完"的定义不是"功能实现了"，而是"能当场演示 + 别人能照着复现"。**

每条 P0 的验收标准因此必须是**可执行的命令**（见第 5–7 节），不能是"实现了 XX 功能"这种描述。

## 2. 非目标（明确不做）

> **这一节和「做什么」同等重要。** 不写下限，执行者会自行脑补，架构会散。

| 不做的事 | 原因 |
|----------|------|
| ❌ 多 Agent **动态** fan-out | 并行会打爆额度（ZCode 3009 已踩过）；opencode 无并行上限可配。v2 最多做**受控的两级子代理** |
| ❌ 前端重写 | v1 的 `static/index.html` 够用。v2 只**新增事件类型**，不改既有五个 |
| ❌ 换鉴权体系（JWT / OAuth / 用户系统） | 单用户自用场景，Bearer Token 足够 |
| ❌ 多租户 / 权限隔离 | 同上 |
| ❌ 迁移 v1 的 ChromaDB 历史数据 | 见 `1-接口冻结.md` 第 4 节，v2 从零开始 |
| ❌ 付费部署 / 域名 / 备案 | v2 定位是本机 + Docker |
| ❌ 换掉手写 agent loop 去用 LangChain | 手写 loop 是 v1 的核心卖点，换掉等于自毁简历 |

## 4. 阶段划分

> **依赖关系**：阶段一是地基，阶段二依赖阶段一埋的点，阶段三依赖阶段一冻结的接口。
> **不允许跳阶段**，也不允许在某阶段内混入下阶段的代码。

**为什么不能先做网关（尽管它是最"炫"的证据）？**

| 如果先做阶段三 | 后果 |
|---|---|
| v2 此刻**没有业务代码**（只有文档与测试） | 网关接不上任何东西 |
| `trace_id` 规范**尚未落地** | 网关自行发明传递方式 → agent 做出来后再对齐 → **返工** |
| 没有指标可采集 | "可观测"是空壳，网关无数据可转 |

**顺序换来的东西**：阶段一结束时，**trace 链路已经能端到端演示**；阶段二结束时，**评估能跑出分数**；
阶段三结束时，**拔主上游服务不倒**。每一步都是一份独立的、可当场展示的证据。

```
阶段一：还债 + 埋点地基     ← 当前在这里
   ↓
阶段二：可观测 + 评估体系
   ↓
阶段三：Go 网关重做（含模型路由与 failover）
   ↓
P1：受控两级子代理（可选）
```

## 6. 阶段二 · 可观测 + 评估体系

### P0 清单

| # | 任务 | 验收标准（可判定） |
|---|------|-------------------|
| 2.1 | **调用指标采集** | 每次 LLM 调用记录：延迟、输入/输出 token、是否命中工具调用、错误码 |
| 2.2 | **工具调用指标** | 每次工具调用记录：工具名、耗时、成功/失败、错误类型 |
| 2.3 | **RAG 指标** | 记录检索命中数、是否降级（embedding 失败）|
| 2.4 | **指标读取接口** | `GET /metrics` 返回结构化 JSON；**不影响**既有接口 |
| 2.5 | **评估集** | ≥30 条用例，覆盖：工具调用正确性、记忆召回、多轮一致性、错误兜底 |
| 2.6 | **离线评估脚本** | 一条命令跑完评估集，输出**可比较的分数**（如工具调用准确率、任务完成率）|

### 阶段二验收命令

```bash
# 跑评估集，输出分数
python -m eval.run --dataset eval/dataset.jsonl

# 读指标
curl -s localhost:8000/metrics | head -50
```

**阶段二完成的定义**：评估脚本能输出一个**可复现的分数**，且改动代码后重跑，分数变化可解释。

> ⚠️ **关键**：评估集必须**先记录基线分数**再开始优化。没有基线的"评估体系"等于没有。

## 7. 阶段三 · Go 网关重做

### P0 清单

| # | 任务 | 验收标准（可判定） |
|---|------|-------------------|
| 3.1 | **多上游路由** | 配置多个上游模型端点，请求能按策略路由 |
| 3.2 | **429/5xx 自动 failover** | 模拟上游返回 429，请求**自动切换**到备用上游且**调用方无感**（同一 `trace_id` 下可见切换记录） |
| 3.3 | **额度/预算控制** | 可按时间窗口设置 token 上限；超限后行为可配置（拒绝 / 降级） |
| 3.4 | **缓存命中统计** | 记录 prompt cache 的命中率 |
| 3.5 | **`trace_id` 注入** | 网关注入的 `X-Trace-Id` 在 agent 日志中可见 |

### 阶段三验收命令

```bash
# 模拟上游故障，验证 failover
curl -s localhost:3000/chat -H "Authorization: Bearer $API_KEY" \
     -H 'Content-Type: application/json' -d '{"message":"test"}'
# 期望：主上游 429 时，请求成功且日志中有切换记录
```

**阶段三完成的定义**：**拔掉主上游，服务仍可用**。

> 💡 **一鱼两吃**：这一层同时是你"模型通道"问题的答案 —— 网关做好后，中转站/官方 API/订阅制都能挂上去做上游，谁挂了自动切。

## 9. 贯穿全程的约束

| 约束 | 说明 |
|------|------|
| 🔒 **接口冻结** | 见 `1-接口冻结.md`；变更必须登记 |
| 🧪 **回归安全网** | **v1 的 5 个测试文件在 v2 任何阶段都必须全绿** —— 这是"重写没退步"的唯一证据 |
| 🚫 **禁止改测试凑绿** | 除「编写测试」任务外，**不得修改任何测试文件**；测试失败只能改实现，不能改断言、不能 skip |
| 📏 **验收即测试** | 每条 P0 的验收标准必须能落成一条可执行的命令或测试 |
| 📝 **P1 不自主决策** | 做完 P0 后**停下等人**，不得自行决定做 P1 |
| 🛑 **阶段间停机** | 每个阶段跑完即停，等人确认后再进入下一阶段（多阶段 checkpoint 策略）|
