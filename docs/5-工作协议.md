# 5 · 工作协议

> **这份文档规定「怎么干活」，不规定「干什么」。** 干什么见 `2-产品规格.md`。
>
> 它是给执行者（opencode）的**行为准则**，也是给人验收时的**检查表**。
> 每条规则都写成"可机械判断"的形式 —— 不写"要仔细"，只写"必须做 X，否则视为失败"。

---

## 0. 六条铁律

违反任意一条，**立即停下报告，不要继续**：

| # | 铁律 | 判断方法 |
|---|------|----------|
| 1 | **禁止修改 `agent-lite/tests/`** | `git diff --stat` 里不得出现该目录 |
| 2 | **禁止谎报结果** | 必须贴**真实命令输出**，不得概括为"测试通过" |
| 3 | **禁止回避失败** | 测试失败只能改实现；不得 skip / xfail / 改断言 |
| 4 | **禁止读 `.env`** | 需要环境变量时只看 `.env.example` |
| 5 | **禁止 `git push`** | 只能本地 `git commit` |
| 6 | **禁止自行决定 P1 项** | 只做当前阶段 P0 清单里的 |

## 1. 先测试，后实现（Test-First）

**要求**：**写任何新功能的代码之前，先写一个验证它的脚本。**

### 1.1 为什么不能"写测试文件"

铁律 1 禁止改 `agent-lite/tests/`。这里的"测试"指的是：

- ✅ **独立验证脚本** —— 放 `agent-lite/verify/` 或临时脚本，不碰 `tests/`
- ❌ 不是往 `tests/` 里加文件（那会污染回归安全网）

### 1.2 具体流程

```
1. 先写验证脚本（它现在必然是失败的 —— 因为功能还没写）
2. 报告：验证脚本写好了，预期它会失败
3. 再写实现
4. 跑验证脚本 → 必须通过
5. 跑回归测试 → 必须仍然全绿
6. 贴出两者真实输出
7. 本地 git commit
```

### 1.3 为什么

没有验证脚本就下手，等于**边写边猜**。猜错了要重写，**花的 token 比重写一遍还多** —— 省钱的方法恰恰是"先想清楚再动手"。

## 2. 失败处理

### 2.1 禁止的回避手段

以下行为**一律视为作弊**，发现即回滚：

- `pytest.skip` / `@pytest.mark.skip` / `xfail`
- 修改断言让测试"看起来过了"
- 删除测试用例
- 注释掉失败的测试
- 在报告里说"测试通过"但实际没跑

### 2.2 正确的失败处理

```
失败 → 读完整报错 → 定位根因 → 改实现 → 重跑 → 贴真实输出
```

**根因找不到时**：停下，把完整报错写进 `QUESTIONS.md`（见第 6 节），**不要瞎改**。

### 2.3 "不要回避挑战" 的正确理解

**回避** ≠ 放弃。
- ❌ **回避**：跳过它、糊弄过去、假装没看见
- ✅ **不回避**：正面尝试 → 失败 → 记录 → 换思路再试 → 再不行就写进 `QUESTIONS.md` 等人

**写进 `QUESTIONS.md` 不是回避**，是承认当前信息不足。**假装解决才是回避。**

## 3. 断线重连（应对上游不稳定）

**背景**：本项目用的中转站存在**间歇性断流**，实测报错为：
```
Error: 模型服务暂时不可用，请稍后重试。
```

### 3.1 单次调用内的重试

遇到上述错误：

1. **等 10 秒，原样重试一次**
2. 仍失败 → **等 30 秒，再试一次**
3. 仍失败 → **换 `cheapai/grok-4.6` 试一次**
4. 仍失败 → 停下，写 `QUESTIONS.md`，报告"上游不可用"

**不允许**：连续快速重试（可能加剧封控）、不允许默默跳过。

### 3.2 任务粒度要小

**每个任务必须能在 30 分钟内跑完。** 任务太大 → 断了就全丢。

- 一个任务 = 一件事（如"迁移 auth.py"），不是"做完阶段一"
- 每个任务结束**必须本地 commit** —— commit 就是存档点，断了能从这里续

## 4. 错误记录（避免重复踩坑）

**项目根维护 `LESSONS.md`**，记录每次踩过的坑。

### 4.1 什么时候写

**每当一个问题花了超过一次尝试才解决**，就追加一条。

### 4.2 格式

```markdown
## [2026-09-23] 问题的一句话描述
- **症状**：看到什么现象（贴原始报错）
- **根因**：实际是什么问题
- **修法**：怎么解决的
- **如何避免**：下次遇到类似情况先检查什么
```

### 4.3 开工前必读

**每个任务开始前，先读 `LESSONS.md`。** 这是"提前避免相同错误"的具体做法 —— 不读就等于没记。

## 5. 依赖自动补齐

**遇到 `ModuleNotFoundError` 时**：

1. 确认缺哪个包
2. **装到正确的解释器**：`D:\Miniconda3\envs\test-env\python.exe -m pip install <包>`
3. 装完**立刻重跑**刚才失败的命令
4. 把新增的包**加进 `agent-lite/requirements.txt`**（否则下次换环境还会缺）

⚠️ **绝对不要**：装到 `my-agent-env`（v1 踩过：该环境依赖不全，会误导）

## 6. 提问机制

**你无法交互式提问**（本环境 `question` 权限被设为 deny）。

需要人决策时，**追加到项目根 `QUESTIONS.md`**：

```markdown
## [任务编号] 一句话说明卡在哪
- **背景**：为什么会遇到
- **选项 A**：<做法> —— 优点 / 缺点
- **选项 B**：<做法> —— 优点 / 缺点
- **我的倾向**：<哪个，为什么>（仅供参考）
- **阻塞程度**：完全阻塞 / 可绕过
```

**"可绕过"的**：写完后跳过它，先做不依赖它的任务。
**"完全阻塞"的**：停下等人。

## 7. 代码自查（提交前）

每个任务 commit 之前，**逐条检查**：

- [ ] 有没有硬编码的模型名？（应读 `MODEL_NAME`）
- [ ] 有没有硬编码的路径 / 端口 / key？
- [ ] 改动的对外接口，是否已在 `docs/1-接口冻结.md` 登记？
- [ ] 新增的报错路径，有没有把错误**如实**返回（而不是吞掉）？
- [ ] 有 `except: pass` 这种吞异常的写法吗？（v1 踩过：RAG 静默失效）
- [ ] 新增依赖有没有写进 `requirements.txt`？
- [ ] 有没有留下调试用的 `print` / 临时文件？

## 8. 前端要求（GUI）

**v1 已有 `static/index.html`（聊天界面）。v2 要求：**

| 项 | 要求 |
|---|---|
| **形态** | 图形界面，**不能是纯终端文本输出** |
| **流式** | **必须是真流式** —— 逐 token 到达，不是攒完一次性吐 |
| **可观测** | 界面上能看到 trace/工具调用过程（阶段二接入 `span` 事件） |
| **观感** | 干净、克制，不要花哨动画；暗色系 |

**"真流式"的验收**：把一个长回复的首字时间（TTFT）和总耗时分开记录 —— 如果首字时间和总耗时接近，说明是**假流式**（先攒后吐）。

## 9. 规划与特化模板协议

### 9.1 模式边界

- **聊天模式**：只收集方向、偏好、目标和约束；不做完整任务拆解，不输出代码，不把未经计划的实现细节甩给用户。
- **计划模式**：读取当前会话事实，选择项目类型模板，查资料，拆解、验收、复核并生成结构化计划。计划本身不是代码。
- 用户已经说过的偏好、约束和禁止项属于任务事实，不得再次询问。
- 只有会改变整体路线，或需要用户自行申请许可/付费的事项，才进入用户可见决策。

### 9.2 计划产物

计划至少包含以下层次：

- `context`：用户事实、已确认决定、默认假设。
- `visible_decisions`：2 到 3 个选项，第一项是可执行默认。
- `hidden_details`：不要求用户逐项决定，但必须完整保留的实现细节、理由和验收。
- `acceptance`：操作步骤、预期结果、验证方式和严重级别。
- `resource_requests`：需要查询端寻找真实资源的申请，未接入时状态必须为 `pending`。
- `risks/notes`：许可、付费、授权、阻塞和无法确认的附加信息。
- `review`：复核状态、维度评分和具体缺口。

不能因为用户不想看细节，就把细节从计划产物中删除；只能在前端默认折叠。

### 9.3 类型模板

通用基座不能被类型模板替换。合并优先级：

```text
用户事实 > 项目范围 > 能力模块 > 类型模板 > 通用默认
```

至少支持以下特化方向：网页、网页游戏、爬虫/数据工具、软件/客户端、后端、移动端和 Agent 应用。

网页游戏必须额外要求：坐标系、状态机、数据不变量、规则常量、边界、输入映射、动画/音效、失焦/后台、真实浏览器测试和压力测试。

网页必须区分静态检查与真实浏览器验收。代码能解析不等于网页完成。

### 9.4 长任务书

十万字任务书不能整段注入上下文。必须先分段、提取目标/约束/偏好/禁止项、去重、检测冲突、记录来源章节，再按当前模板选择相关内容。

### 9.5 失败纪律

- 计划工具参数错误：读取会话事实，最多恢复一次。
- 恢复后最多复核一次；复核失败必须标记 `unavailable`，不得伪造高分。
- 计划模式不能把工具错误直接作为最终计划回复。
- 每个 `tool_call_id` 必须有对应 `tool` 消息，不能为了界面去重而破坏协议。

## 10. 成本纪律

**预算有限（先充 ¥20）**，因此：

| 规则 | 说明 |
|---|---|
| **小步快跑** | 每个任务小且可验证 —— 跑飞了损失可控 |
| **先测后写** | 见第 1 节，避免返工（返工最烧钱） |
| **禁止无意义探索** | 不要为了"看看"而乱读一大堆文件 |
| **每任务结束上报** | 报告里写清这次大概消耗多少（供人判断预算） |

## 11. 任务收尾格式

每个任务完成后，**必须**按此格式汇报：

```
任务：<编号与名称>
改动文件：<列表>
验证命令：<原样命令>
真实输出：<粘贴，不要概括>
回归测试：<真实输出>
LESSONS.md 新增：<有无，写在第几条>
遗留问题：<有就写，没有写"无">
```

**缺任何一项都视为任务未完成。**
