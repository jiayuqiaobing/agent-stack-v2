# 3 · 可观测数据模型

> **这份文档是「可观测」「评估体系」「多 Agent」三层共同依赖的契约。**
> 它规定的不是"怎么实现"，而是 **trace / span 长什么样、怎么传、存哪里**。
>
> 一旦定稿，**阶段二和三都不得自行发明字段** —— 要加字段先改这份文档。
>
> 前置阅读：`1-接口冻结.md`（既有契约）、`2-产品规格.md`（阶段一 P0 1.6）

---

## 1. 为什么先做这个

v2 的三个新能力有严格的依赖关系：

```
多 Agent 编排        ← 需要父子关系，否则调用链断裂
      ↑
评估体系             ← 需要原始数据，否则评估不了
      ↑
可观测（trace/span） ← 地基
```

**如果先做多 Agent、后补 trace**：所有既有的 agent 调用都没有 `parent_span_id`，**整条链路要推倒重来**。
所以必须先定数据模型，再写业务代码。

---

## 2. 核心概念

| 概念 | 定义 | 生命周期 |
|------|------|----------|
| **trace** | 一次完整的用户请求（从收到 HTTP 到返回） | 一次请求 = 一棵树 |
| **span** | trace 树上的一个节点，代表一段有始有终的工作 | 每个操作 = 一个节点 |
| **session** | 跨多次请求的对话上下文（**v1 已有，与本模型正交**） | 多轮对话 |
| **trace_id** | 一棵 trace 树的唯一标识 | 贯穿全链路 |
| **span_id** | 单个节点的唯一标识 | 单个操作 |

> ⚠️ **`session_id` 和 `trace_id` 是两个维度，不要混**：
> 一个 session（多轮对话）会产生**多个** trace（每轮一个）。RAG 隔离用 `session_id`，链路追踪用 `trace_id`。

---

## 3. ID 方案

| 字段 | 格式 | 生成方 | 说明 |
|------|------|--------|------|
| `trace_id` | 32 位小写 hex（16 字节） | **网关生成**（直连 agent 时由 agent 兜底） | 与 W3C Trace Context 一致 |
| `span_id` | 16 位小写 hex（8 字节） | 每个 span 的创建者 | 与 W3C Trace Context 一致 |

**为什么用 W3C 格式而不是随便的 uuid**：
- 16 字节 trace_id / 8 字节 span_id **就是 W3C Trace Context 标准**，将来接 OpenTelemetry、Jaeger、任何 APM 都不用改
- 面试时这一句就能体现"你知道业界标准长什么样"

```python
import secrets
trace_id = secrets.token_hex(16)   # 32 hex chars
span_id  = secrets.token_hex(8)    # 16 hex chars
```

> **v1 的 `session_id` 是 `uuid4().hex[:8]`（8 位）**，那是会话标识，格式不变，**不要拿来当 trace_id**。

## 4. Span 结构

### 4.1 字段定义

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `trace_id` | string | ✅ | 32 位 hex |
| `span_id` | string | ✅ | 16 位 hex |
| `parent_span_id` | string \| null | ✅ | 根 span 为 `null` |
| `name` | string | ✅ | 操作名，见 4.2 命名规则 |
| `kind` | string | ✅ | 取值受控，见第 5 节 |
| `start_time` | float | ✅ | Unix 时间戳（秒，含毫秒小数） |
| `end_time` | float \| null | ✅ | 未结束为 `null` |
| `duration_ms` | float \| null | ✅ | `end_time` 有值时才计算 |
| `status` | string | ✅ | `"ok"` \| `"error"` \| `"unset"` |
| `error` | object \| null | ⬜ | `{type, message}`，仅 `status="error"` 时 |
| `attributes` | object | ✅ | 按 `kind` 定义的业务字段，见第 5 节。无内容时用 `{}` |
| `session_id` | string | ✅ | 关联到既有 session，便于按会话查询 |

### 4.2 命名规则

`name` 必须**低基数**（不能把用户输入拼进去，否则指标无法聚合）：

| kind | name 取值 |
|------|-----------|
| `agent` | `"agent.turn"` |
| `llm` | `"llm.chat"` |
| `tool` | `"tool.{工具名}"`（如 `tool.calculate`） |
| `rag` | `"rag.search"` / `"rag.write"` |
| `memory` | `"memory.summarize"` |

> ❌ 反例：`name = "tool.read_file(/some/path)"` —— 路径是高基数字段，应放进 `attributes`，不进 `name`。

---

## 5. span kind 与业务字段

| kind | 表示 | `attributes` 必填字段 |
|------|------|----------------------|
| `agent` | 一次 agent 循环（含多步） | `steps`(int) `max_steps`(int) `terminated_by`("reply"\|"max_steps"\|"error") |
| `llm` | 一次模型调用 | `model`(str) `prompt_tokens`(int) `completion_tokens`(int) `cache_hit_tokens`(int) `has_tool_calls`(bool) |
| `tool` | 一次工具调用 | `tool_name`(str) `source`("local"\|"mcp") `success`(bool) `error_type`(str\|null) `args_size`(int) |
| `rag` | 一次检索或写入 | `k`(int) `hit_count`(int) `degraded`(bool) |
| `memory` | 一次记忆压缩 | `before_count`(int) `after_count`(int) `summary_len`(int) |

**字段说明：**

- `llm.cache_hit_tokens` —— **本项目的关键指标**。v1 的 `build_context()` 特意把不变的 system prompt 放最前（100% 缓存命中），这个字段就是验证该设计是否真的生效的证据。
- `tool.args_size` —— 只记 `len(str(args))`，**不记参数内容**（可能含路径等敏感信息）
- `rag.degraded` —— v1 的 embedding 静默失效踩过大坑，这个布尔值专门用来暴露降级

## 6. 传播方式

### 6.1 HTTP 层

| Header | 方向 | 说明 |
|--------|------|------|
| `X-Trace-Id` | 网关 → agent-lite | 32 位 hex；agent 收到则沿用，收不到则**自己生成**（兜底） |
| `X-Parent-Span-Id` | 网关 → agent-lite | 可选。若网关自己产生 span，则传它的 span_id |

**规则：**
1. 客户端**也可以**带 `X-Trace-Id`（便于跨系统串联）—— **但必须校验格式**，非法值一律丢弃并重新生成（防注入）
2. agent-lite **必须**在响应头回写 `X-Trace-Id`，便于调用方对账
3. Go 网关透传 `X-Trace-Id`，**不拦截、不覆盖**

### 6.2 进程内传播

Span 需要一个"当前上下文"，让深层函数不用层层传参就能拿到 `parent_span_id`：

```python
# 推荐形态（contextvars，异步安全）
from contextvars import ContextVar
_current_span: ContextVar[str | None] = ContextVar("current_span", default=None)
```

> **不推荐**把 span_id 当参数一路往下传 —— `agent.py` → `execute_tool()` → `_call_mcp_tool()` 这条链已经很深了，加参数会污染所有函数签名。
> **也不推荐**全局变量 —— v1 已经踩过"多 session 交叉"的坑（虽然那是数据隔离问题，但根因相同：**共享可变状态**）。

### 6.3 SSE 层

新增 SSE 事件类型（**只加不改 —— 见 `1-接口冻结.md` 第 1.2 节**）：

```json
{"type": "span", "span": { ...上面的 span 结构... }}
```

前端遇到未知 `type` 应**忽略而非报错**。v2 前端若不消费这个事件，行为必须与 v1 完全一致。

## 7. 采集与存储

### 7.1 采集点（对应 `2-产品规格.md` 阶段二 P0）

| 位置 | 产出的 span |
|------|-------------|
| `router.py` 的 `/chat` `/chat/stream` | 根 `agent.turn` |
| `agent.py` 每轮循环 | `llm.chat` |
| `agent.py` 工具分派 | `tool.{name}` |
| `rag_store.py` 的 `add` / `search` | `rag.write` / `rag.search` |
| `memory.py` 的 `_generate_summary` | `memory.summarize` |

### 7.2 存储方案

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **JSONL 追加写** | 零依赖、可直接 grep、崩溃不丢已写数据 | 查询要自己实现 | ✅ **阶段二采用** |
| SQLite | 可 SQL 查询 | 并发写要加锁 | 🟡 量大了再换 |
| Prometheus / OTel | 生态完整 | **引入重依赖，与"手写"的项目定位冲突** | ❌ 不用 |

**文件位置**：`logs/spans-YYYY-MM-DD.jsonl`（与既有 `logs/` 目录一致，**已在 `.gitignore` 中**）

**一行一个 span**（JSONL，不是 JSON 数组）—— 追加写，进程崩溃也不丢已落盘的数据。

## 8. 读取接口

### `GET /metrics`

**只读、不改任何既有接口**。返回聚合指标，**不返回原始 span**（原始数据在 JSONL 里，用 `grep` / `jq` 查）。

```json
{
  "window": "24h",
  "requests": {"total": 120, "ok": 117, "error": 3, "error_rate": 0.025},
  "latency_ms": {"p50": 1200, "p95": 4300, "p99": 8100},
  "llm": {
    "calls": 245,
    "prompt_tokens": 120400,
    "completion_tokens": 18300,
    "cache_hit_tokens": 98500,
    "cache_hit_rate": 0.818
  },
  "tools": {
    "calls": 88,
    "success_rate": 0.943,
    "by_name": {"calculate": 40, "read_file": 32, "get_time": 11, "weather": 5}
  },
  "rag": {"searches": 60, "avg_hit_count": 2.4, "degraded_count": 0}
}
```

**设计要求：**
- 聚合在**读取时**计算，不在写入时计算（写入要保持零开销）
- `cache_hit_rate` 低于 0.5 时应在响应中给出提示 —— 这是 v1 前缀缓存设计失效的早期信号

## 9. 与既有设计的边界（不要越界）

| 既有设计 | 本模型的态度 |
|----------|-------------|
| `session_id` 与 ChromaDB 隔离 | ✅ **完全不动**。trace 是旁路观测，不参与记忆隔离 |
| SSE 五种既有事件 | ✅ **只加 `span`，不改旧的五个** |
| `HybridMemory` 的 `summary_trigger` / `keep_recent` | ✅ **不动**，只在压缩时加一个 `memory.summarize` span |
| 手写 agent loop | ✅ **不动**，只在循环内外加埋点 |
| 前端 `static/index.html` | ✅ **不改**（除非做 P1.2）|

> **核心原则：可观测是旁路，不是主路。** 任何埋点都不得改变既有业务逻辑的行为和结果。
> 验收方式：**埋点前后，v1 的 5 个回归测试必须输出完全一致的结果。**
